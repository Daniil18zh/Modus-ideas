# «Модус Идеи» — продуктовая и техническая концепция

Решение для трека «Система обратной связи и предложений сотрудников» хакатона ГК «Модус Трейд». Формат результата — **работающий MVP** (п. 4.3 ТЗ).

## 1. Проблема и ценность

**Проблема.** О проблемах сообщают письмами, в чатах и устно. Обращения теряются, ответственный не назначен, автор не знает, чем всё закончилось. Разбор чужих проблем для сотрудника — дополнительная рутина без видимой пользы, поэтому её откладывают.

**Решение.** Единая доска проблем и решений внутри Telegram, где компания уже общается. Каждое обращение становится карточкой с ответственным, сроком и наградой. Решения ищет вся команда, лучшее выбирает руководитель. Участие вознаграждается Модус-коинами, которые меняются на реальные бонусы.

**Ценность для компании:**
- обращения не теряются: у каждого статус, срок, ответственный, история, а просрочки попадают в утреннюю сводку;
- прозрачность: автор видит ход работы и результат, а клиент — статус по ссылке;
- поток идей: решения предлагают все, а не только назначенный исполнитель;
- база знаний: проблемы, решения и итоги сохраняются, их можно искать;
- выявление повторяющихся проблем: подсказка похожих обращений и аналитика по категориям и точкам QR.

## 2. Пользователи и сценарии

| Роль | Ключевая потребность |
|---|---|
| Сотрудник | Быстро сообщить о проблеме, предложить идею, узнать результат, получить признание |
| Руководитель | Видеть все проблемы своей зоны, выбирать решения, контролировать сроки |
| Администратор | Настраивать категории, маршрутизацию и награды, подтверждать обмены |
| Клиент (следующий этап по ТЗ, включён в MVP) | Сообщить о проблеме без регистрации и узнать результат |

**Основной сквозной сценарий (реализован):**
1. Сотрудник нажимает «+», выбирает категорию, описывает проблему и, при желании, решение. Если похожая карточка уже есть, система её подскажет.
2. Карточка появляется в колонке «Новое». Бот публикует её в рабочей группе и присылает ответственному за категорию.
3. Коллеги нажимают «Подключиться», предлагают решения и голосуют за лучшие. Карточка переходит в «Обсуждение».
4. Руководитель выбирает лучшее решение. Автор решения получает награду и становится исполнителем, карточка переходит «В работу».
5. Исполнитель внедряет решение и нажимает «Сдать на проверку» с отчётом.
6. Руководитель принимает работу. Начисляются коины: исполнителю за внедрение и за срок, всем предложившим, автору обращения. Автор получает уведомление с итогом.
7. Сотрудник меняет коины на награду, администратор подтверждает обмен.

**Клиентский сценарий:** QR на объекте → форма → карточка с пометкой «QR» и высоким приоритетом → сценарий выше → клиент видит статус и ответ компании по ссылке.

## 3. Мотивация: Модус-коины

Цель — превратить рутину в соревнование с понятной наградой и при этом не дать системе вырасти в «накрутку».

- **Награда видна заранее** на каждой карточке. Она зависит от приоритета, руководитель может её изменить.
- **Платят за результат, а не за активность.** Основные коины начисляются только после выбора руководителем и приёмки работы. За предложение даётся +5 и только когда задача закрыта.
- **«Горящие» задачи** — главный механизм против того, чтобы рутину сливали. Если за 48 ч задачу никто не взял, награда растёт на 20% в сутки, до ×2. Неудобные задачи со временем становятся самыми выгодными.
- **Бонус за срок** (+20) и публичный рейтинг месяца поддерживают темп.
- **Уровни и достижения** («Пожарный», «Точно в срок», «Решала») дают признание без денег.
- **Магазин** с наградами разной цены: от обеда до путёвки. Каждый обмен подтверждает администратор, и это точка финансового контроля.

**Защита от злоупотреблений:** нельзя голосовать за своё решение. Исполнитель не принимает собственную работу. Повторная приёмка и повторный выбор победителя заблокированы на уровне БД. Списание при обмене атомарное: при нехватке баланса обмен не проходит. Ручные начисления видны в истории.

Экономика по умолчанию: средняя задача приносит исполнителю 60 + 30 + 20 = 110 МК. Путёвка (6000 МК) — это около 55 решённых задач, то есть год активной работы. Премия 3 000 ₽ — примерно 3 задачи.

## 4. Процесс рассмотрения (п. 2.5 ТЗ)

| Вопрос ТЗ | Как решено |
|---|---|
| Как обращение попадает к ответственному | У категории есть ответственный, он получает уведомление в личку. Если ответственного нет, уведомление получают все руководители. Дублируется в рабочую группу |
| Как фиксируются статус и результат | Статусы Новое → Обсуждение → В работе → На проверке → Решено/Отклонено. Переходы разрешены по ролям. Итог (resolution) обязателен при сдаче, отклонении и приёмке. Каждое действие пишется в историю |
| Как автор узнаёт о ходе работы | Уведомления бота при выборе решения, комментарии, закрытии и отклонении. Раздел «Мои». Клиент — страница статуса |
| Как предотвращается потеря | Дедлайн по приоритету (24 ч / 72 ч / 7 дн), подсветка просрочки, утренняя сводка в группе, рост награды у «горящих», метрика «время до первой реакции» |
| Как выявляются повторы | Подсказка похожих обращений при создании, статистика по категориям за 30 дней и по точкам QR, отклонение «дубликат #N» |

## 5. Доступ и конфиденциальность (п. 2.6 ТЗ)

| | Сотрудник | Руководитель | Администратор | Клиент |
|---|---|---|---|---|
| Создать обращение | ✓ | ✓ | ✓ | ✓ (QR, только публичные категории) |
| Видеть доску, решения, комментарии | ✓ | ✓ | ✓ | только свой статус по секретной ссылке |
| Видеть контакты клиента | — | ✓ | ✓ | — |
| Предлагать и голосовать | ✓ | ✓ | ✓ | — |
| Выбрать победителя, менять параметры, принять или отклонить | — | ✓ | ✓ | — |
| Сдать на проверку | исполнитель | ✓ | ✓ | — |
| Аналитика | — | ✓ | ✓ | — |
| Обмены, роли, QR, справочники | — | — | ✓ | — |

**Анонимность.** Автор может скрыть имя. В интерфейсе и API его не видит никто, включая руководителей. В базе автор хранится, чтобы прислать уведомление и начислить коины. Ограничение: при необходимости уточнить детали руководитель пишет комментарий в карточке, лично связаться с автором он не может.

**Защита данных.** Подпись Telegram `initData` проверяется по HMAC-SHA256 на каждом запросе, срок жизни 24 ч. Доступ только у участников привязанной группы, членство перепроверяется раз в 6 ч, а выход из группы закрывает доступ. Секреты хранятся в Cloudflare Secrets. Webhook бота проверяется секретным заголовком. Публичная форма защищена honeypot-полем и лимитом 5 обращений в час с IP (в базе хранится только хеш IP). Токен статуса клиента — 128 бит случайности. Все SQL-запросы параметризованы, весь вывод в интерфейсе экранируется.

## 6. Техническая концепция

```
Telegram (группа, бот, Mini App)      Клиент (браузер, QR)
          │ initData                         │
          ▼                                  ▼
 ┌──────────────── Cloudflare Worker (src/index.js) ────────────────┐
 │ Static Assets: public/  │  /api/*  │  /api/public/*  │ /tg/webhook │
 │ роли · статусы · коины · уведомления · Cron 09:00 МСК             │
 └───────────────┬──────────────────────────────────┬───────────────┘
                 ▼                                  ▼
          Cloudflare D1 (SQLite)            Telegram Bot API
```

**Почему этот стек:**
- Telegram — канал, который у сотрудников уже есть: не нужно устанавливать приложения и заводить пароли. Mini App даёт полноценный интерфейс.
- Cloudflare Workers + D1 бесплатно покрывают десятки тысяч запросов в день, не требуют серверов и разворачиваются одной командой.
- Чистый JS без сборки: проще поддерживать, быстрее загружается в Telegram.

**Данные:** `users`, `categories` (с ответственным = маршрутизация), `tickets`, `solutions`, `solution_votes`, `participants`, `comments`, `events` (аудит), `coin_tx` (журнал коинов, баланс выводится из него), `rewards`, `redemptions`, `qr_points`, `settings`.

## 7. Интеграции (п. 3.4 ТЗ, следующий этап)

| Система | Цель | Данные и направление | Способ |
|---|---|---|---|
| Битрикс24 | Карточка, принятая в работу, становится задачей Б24 у исполнителя. Синхронизация статуса | Модус Идеи → Б24: заголовок, описание, исполнитель, срок. Б24 → Модус Идеи: статус | REST API Б24 (`tasks.task.add`), входящий вебхук, исходящий вебхук на изменение |
| Битрикс24 / кадры | Подтягивать отдел и руководителя сотрудника | Б24 → Модус Идеи | `user.get` по сопоставлению Telegram ↔ сотрудник |
| 1С ЗУП / УТ | Премии из магазина начисляются автоматически | Модус Идеи → 1С: сотрудник, сумма, основание | HTTP-сервис 1С или выгрузка реестра одобренных обменов |
| 1С УТ | Привязать клиентское обращение к контрагенту или объекту | 1С → Модус Идеи: справочник объектов | Выгрузка справочника, QR-точка = объект |

Перед реализацией нужно уточнить: доступ к REST Б24 (вебхук или приложение), правила сопоставления учётных записей, способ проведения премий в 1С, требования ИБ к хранению персональных данных.

## 8. Этапы развития

| Этап | Состав |
|---|---|
| **MVP (готов)** | Вход через Telegram и группу, доска, решения, голосование, выбор победителя, статусы и сроки, уведомления, QR-форма клиента, коины, уровни, достижения, рейтинг, магазин, аналитика, справочники |
| **Этап 2** | Вложения (фото, файлы) в R2, напоминания исполнителю перед дедлайном, экспорт в Excel, шаблоны ответов клиентам, уведомления клиента по e-mail |
| **Этап 3** | Интеграция с Битрикс24 и 1С, опросы и NPS для клиентов по тем же QR, ИИ-кластеризация похожих обращений и подсказка решений из базы |
| **Требует отдельной проработки** | Юридическое оформление нематериальных и денежных наград, политика хранения ПДн клиентов, SSO с корпоративным каталогом |

**Как проверить полезность (пилот на 1–2 подразделениях, 1 месяц).** Метрики из раздела «Аналитика»: доля рассмотренных обращений, время до первой реакции, доля с зафиксированным результатом, число реализованных улучшений, доля сотрудников, предложивших хотя бы одно решение. Плюс опрос удовлетворённости авторов.

## 9. Допущения

- У всех сотрудников есть Telegram, и они состоят в рабочей группе.
- Состав и цены наград — пример; финальные значения согласует руководство.
- Демо-данные синтетические (п. 3.5 ТЗ).
